# Generating typed decoders with `msggen`

`msggen` turns `.msg` schemas into a Go file with one struct and one decoder per message type — a
typed, allocation-conscious alternative to decoding every message generically through
`ros2msg.Schema.Decode` (see [decoding.md](decoding.md) for that approach and when to prefer it).

Install it alongside your project, or build it from the module:

```sh
go install github.com/acristoffers/foxglove-client-go/cmd/msggen@latest
```

## Workflow

`msggen` has two subcommands, meant to be run in sequence and the first one re-run whenever the live
system's message definitions might have changed:

```sh
# 1. Fetch schemas from a running server, by topic or by type, into a
#    directory of .msg files (one per type, dependencies included).
msggen fetch -url ws://localhost:8765 -dir schemas /odom sensor_msgs/msg/Imu

# Re-running with no arguments refreshes every schema already in the
# directory, which is convenient after upgrading the ROS packages involved.
msggen fetch -url ws://localhost:8765 -dir schemas

# 2. Generate the Go file from whatever is in the schema directory.
msggen gen -dir schemas -pkg msgs -out messages_gen.go
```

`fetch` connects to the server, waits for the requested topics/types to be advertised (`-timeout`,
default 5s), and writes each type's `ros2msg`-encoded schema to `<dir>/<package>/msg/<Type>.msg` —
the same layout `ros2msg.Parse` expects a schema's dependencies to be organized in conceptually,
though here each type gets its own file rather than one concatenated blob. Commit this directory:
it's the durable record of exactly which message layouts your generated code was built against, and
lets `gen` run again later (e.g. in CI) without a live server.

`gen` reads every `.msg` file under `-dir`, and fails loudly if two schemas disagree about a type
they both use — i.e. if `/odom` and `/imu` were fetched at different times from systems with
incompatible definitions of a shared type like `std_msgs/Header`, `gen` refuses to generate code for
it rather than silently picking one. Re-`fetch` to resolve it.

## What gets generated

For a schema with a message like:

```
# pkg/msg/Sample.msg
uint8 MODE_A=1
Item[] items
float64[<=3] bounded
```

`gen` produces (abbreviated):

```go
// Code generated by msggen. DO NOT EDIT.

package msgs

import "github.com/acristoffers/foxglove-client-go/cdr"

// Message is implemented by every generated message type.
type Message interface {
	SchemaName() string
	Fingerprint() string
	UnmarshalCDR(data []byte) error
}

// PkgSample is the pkg/msg/Sample message.
type PkgSample struct {
	Items   []PkgItem
	Bounded []float64
}

const PkgSample_MODE_A uint8 = 1

func (*PkgSample) SchemaName() string   { return "pkg/msg/Sample" }
func (*PkgSample) Fingerprint() string  { return "a1b2c3d4e5f6a7b8" }
func (m *PkgSample) UnmarshalCDR(data []byte) error { return unmarshalCDR(data, m.decode) }

func (m *PkgSample) decode(r *cdr.Reader) {
	m.Items = make([]PkgItem, r.SequenceLength(4))
	for i := range m.Items {
		m.Items[i].decode(r)
	}
	m.Bounded = make([]float64, r.SequenceLength(8))
	for i := range m.Bounded {
		m.Bounded[i] = r.Float64()
	}
}
```

Points worth knowing before you rely on the generated code:

- **Type names** drop the conventional ROS package suffix and CamelCase the rest:
  `geometry_msgs/Point` → `GeometryPoint`, `example_interfaces/Int32` → `ExampleInt32`,
  `tf2_msgs/TFMessage` → `Tf2TFMessage`.
- **Field names** are CamelCased from `snake_case`, with a short table of initialisms kept
  upper-case (`frame_id` → `FrameID`, `cpu_usage` → `CPUUsage`). A field whose generated name
  collides with one of the `Message` interface's methods (`SchemaName`, `Fingerprint`,
  `UnmarshalCDR`) gets a trailing underscore to disambiguate it from the method.
- **Constants** become package-level `TypeName_CONSTANT` declarations typed to match the field
  they'd be compared against.
- **Fixed byte-like arrays** (`uint8[N]`, `byte[N]`, `char[N]`) generate as Go `[N]byte` and are
  decoded with a single `copy`, not a per-element loop. Unbounded/bounded byte-like arrays
  (`uint8[]`, `uint8[<=N]`) use `r.Bytes(...)` directly for the same reason.
- **`Fingerprint()`** is baked in at generation time from `ros2msg.Schema.Fingerprint`. Compare it
  against a live channel's schema fingerprint (computed the same way from the channel's advertised
  schema) if you want to detect at runtime that the running system's message layout has drifted from
  what the code was generated against, before trusting `UnmarshalCDR` not to silently misinterpret
  bytes.
- **`wstring`** fields are rejected at generation time (`gen` errors out), matching
  `ros2msg`/`cdr`'s lack of support for it.

## Using generated types

```go
case foxglove.MessageData:
	if ev.Channel.Topic == "/odom" {
		var msg msgs.NavOdometry
		if err := msg.UnmarshalCDR(ev.Data); err != nil {
			log.Println("decode /odom:", err)
			break
		}
		fmt.Println(msg.Pose.Pose.Position.X)
	}
```

Every generated type satisfies the generated `Message` interface, which is handy for code that
dispatches on schema name without a type switch over every concrete type:

```go
func handle(schemaName string, data []byte, byName map[string]func() msgs.Message) {
	newMsg, ok := byName[schemaName]
	if !ok {
		return
	}
	msg := newMsg()
	if err := msg.UnmarshalCDR(data); err != nil {
		log.Println(err)
		return
	}
	// msg.SchemaName(), msg.Fingerprint() available for logging/validation
}
```

The generated file has no dependency on `foxglove` or `ros2msg` at runtime — only on `cdr`, which it
imports directly — so it's safe to vendor the generated file into a different module than the one
running `msggen`, as long as that module also depends on this one for the `cdr` package.
